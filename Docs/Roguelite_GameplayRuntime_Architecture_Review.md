**总体判断：这份方案的主干合理，能够落地；但作为“可以直接指导实现的最终设计”，目前还不够。**

它对 **Modifier 的统一语义、Feature 的能力授予、多来源追踪和数值解释** 做了有价值的补充，我会采纳。但它对中央查询、缓存、状态变化通知、来源身份及 UE 生命周期的处理还不完整。直接按目录和接口开工，容易得到“概念分得很清楚，运行时却到处补同步逻辑”的系统。

我已完整阅读这份文档的第 0～48 节，并重新核对了现有 Combat、Gunner、人口、幻化相关代码及 Epic 官方资料。本轮没有修改任何文件，也没有执行编译或运行测试。

| 评审维度 | 判断 |

| 总体方向 | 合理，值得作为下一版设计基础 |

## 一、它对原方案的哪些修改，我赞同

**1．第一版取消“开局选择构筑主题”，我接受这个调整。**

我之前的方案偏向解决未来卡池扩大后的问题。现在内容尚少，额外增加一次开局选择，确实不一定值得。

首版用合法候选筛选，加上已经形成路线的轻度权重支持，更简单。

但 `1.2～1.4` 只是待验证参数，不是已经成立的平衡结论。支持力度必须有上限，也要防止第一次选择过早锁定整局路线。

**2．把 Modifier 明确为底层数值表达，是有效补充。**

`Target＋Operation＋Magnitude＋Requirement＋Source` 比笼统的“添加一个属性加成”清楚。

尤其是：

- 伤害提高多少；
- 适用于谁；
- 适用于哪个技能；
- 来自哪里；
- 撤销时撤销哪一份。

这些应该在数据中能够解释，不能靠散落的角色类型判断补齐。

**3．Feature 作为“能力授予”的语义值得保留。**

“允许穿透”和“穿透数量增加”不是同一个问题。独立描述能力是否获得，有助于表达解锁、互斥和临时授予。

不过，**需要 Feature 这个概念，不等于每个能力都必须额外经过一个 FeatureComponent。** 后面会具体说明。

**4．Explain 应尽早建设，我赞同。**

这是这份文档最值得采纳的补充之一。

但首版可以只是按需输出结构化计算明细或调试日志，不需要先做专门的调试界面、历史数据库和全量追踪系统。

**5．不建设通用事务框架，我也赞同。**

合体可以先由一个明确的 `TryFusion` 流程负责。

这里应区分：

> 不需要通用事务框架，但仍需要完整的失败处理。

我之前强调的预留、提交与回滚是正确性要求，不是要求建立一个数据库式框架。

## 二、最需要修改的问题：中央查询＋Revision 缓存没有完成运行时闭环

对应文档[第 19～20 节](C:/Users/gh/Downloads/MineLearning_Roguelite_GameplayRuntime_Architecture.md:1864)。

文档建议：

```text
RunBuild 保存修饰
单位查询时自动匹配
RunModifierRevision 改变后重新计算缓存
```

这个方案**可以成立**，但现在只解决了“查询能算对”，没有解决“状态变化如何生效”。

举一个当前项目马上会碰到的例子：

```text
当前生命 50 / 100
获得最大生命 +100%
```

按文档规则，应立即变成：

```text
100 / 200
```

如果只是让 `GetMaxHealth()` 下次查询时返回 200：

- 谁负责把当前生命改成 100？
- 如果始终没有查询，会不会一直保持错误状态？
- 如果在 Getter 里面顺手修改生命，就违反了查询无副作用。
- UI 和技能什么时候收到变化通知？

移速也一样。现有 OreBuddy 冲刺逻辑持续写入 `MaxWalkSpeed`，它不会因为中央 Resolver 的结果变化就自动使用新速度。

因此，必须明确区分：

| 数据用途 | 合适的处理 |
|---|---|
| 本次伤害、技能参数查询 | 在明确的求值时机读取 |
| 生命上限变化引起当前生命调整 | 修饰提交时主动处理 |
| 移动速度等执行配置 | 变化后通知执行者更新 |
| UI 展示 | 状态变化事件＋首次同步 |

**我的建议：首版先不要引入惰性版本缓存。**

使用一个本局修饰集合和一个单位局部修饰集合，统一计算；构筑或局部效果发生变化时，对已登记单位发布变化通知。真实出现性能问题以后再缓存。

即使以后缓存，单独一个 `RunModifierRevision` 也不够，因为以下变化都可能改变结果：

- 单位局部 Effect 增加、到期；
- 控制模式从 AI 变为玩家；
- 单位标签或基础配置变化；
- 技能不同；
- 伤害目标不同，例如普通矿物与 Boss。

尤其“对 Boss 增伤”不能缓存成单位唯一的最终伤害倍率。

**中央保存还是单位登记，不存在绝对正确的一方。** 文档把“新单位出生时装配本局能力”整体判成错误，过于绝对。由统一的单位注册入口执行幂等装配，同样是正常设计；真正要避免的是多个 Spawn 路径各自补一遍不同逻辑。

## 三、中央查询还需要解决依赖方向和所属玩家

文档一方面禁止基础层认识 `RunBuild`，另一方面又要求单位求值时读取 `RunBuild Modifier`。

这不是不能实现，而是缺少中间的数据边界。

建议表达为：

```text
RunBuild
→ 生成/更新中立的修饰集合
→ 装配给单位的求值上下文

Resolver
→ 只读取修饰集合与上下文
→ 不查找 RunBuild、Talent 或 Demo
```

这里可以是一个普通值对象或明确的数据源引用，不必再建立一套复杂 Service。

还必须明确：

> “所有 Gunner”是哪个玩家或阵营拥有的 Gunner？

`Unit.Gunner` 只能表示类型，不能表示归属。将来存在敌方 Gunner、第二名玩家或中立单位时，仅靠类型标签会串加成。

**所属玩家/阵营、当前控制者、UE Actor Owner 是不同概念。** 不应默认 `IsPlayerControlled()` 或 `GetOwner()` 就能回答“这台机器人属于哪套构筑”。

这也是低耦合设计需要的实际输入，不能只靠禁止 `Cast<AGunnerCharacter>()` 来保证。

## 四、Feature 的方向对，但“解锁”“拥有”“执行”必须分开

对应[第 6、14、18、43 节](C:/Users/gh/Downloads/MineLearning_Roguelite_GameplayRuntime_Architecture.md:963)。

文档里出现了：

```text
Talent 解锁 Feature
→ 本局 Gunner 可以触发 GoldenHit
```

这可能是有意设计，也可能是不小心混淆了两个概念。

至少应该区分：

| 语义 | 含义 |
|---|---|
| Unlock | 以后允许获得，例如某强化进入候选池 |
| Grant | 当前主体实际获得该能力 |
| Execute | 当前满足执行条件，实施能力行为 |

所以天赋应明确选择：

```text
解锁黄金爆头强化的获取资格
```

或者：

```text
每局开局直接授予黄金爆头能力
```

两种都合理，但不能使用同一个模糊的 `UnlockFeature` 同时表达。

**FeatureRuntime 管理的应该是授予状态，不是具体行为实现。**

技能读取能力状态并执行穿透，这种局部判断没有问题：

```cpp
if (HasPiercingCapability())
{
    // 执行已经实现的穿透规则
}
```

但如果未来出现几十个互相组合的分支，Feature 标签本身不会自动解决行为组合问题。仍需确定穿透、分裂、爆炸的执行顺序、目标去重及互斥关系。

也不能机械要求所有行为都同时拥有一个开关和一个参数：

```text
HasPierce = false
PierceCount = 3
```

如果项目语义本来就是“额外穿透数量大于 0 即可穿透”，那么独立保存 `HasPierce` 可能只是制造冲突状态。

只有“获得资格但暂时被禁用”等真实需求存在时，才值得分别表示。

**多来源授予值得保留，但来源必须是实例身份。**

如果两个独立 Effect 都授予同一种能力：

```text
同一种 Effect，第一个实例
同一种 Effect，第二个实例
```

不能仅以 Effect 定义 ID 放进 `TSet`，否则会合并成一个来源，删除任一实例就可能误关能力。

另外还需要明确：能力在一次技能执行中被撤销，是立即取消，还是本次继续、下次失效。单纯 `HasFeature()` 不足以表达这一点。

## 五、Modifier 的统一表达还存在几个语义缺口

**1．Source 被用来表示了两种不同的东西。**

在[第 3.4 节](C:/Users/gh/Downloads/MineLearning_Roguelite_GameplayRuntime_Architecture.md:592)，`Source.UnitType` 指伤害发起单位；在第 3.5 节，Source 又指 Talent、Upgrade、Effect 的贡献来源。

假设辅助单位给 Gunner 施加射速 Buff：

- 施加者是辅助单位；
- 被修饰主体是 Gunner；
- 贡献来源是某个 Effect 实例。

三者不能混为一谈。

建议用明确语义区分：

- `Origin`：这份贡献来自哪个内容及运行时实例；
- `Subject`：当前求值的单位；
- `DamageSource / DamageTarget`：本次伤害双方。

具体字段名可以调整，但业务概念必须分开。

**2．底层来源类型不应该专门依赖 Effect。**

文档的 `FModifierSource` 使用 `FEffectHandle` 表示运行时来源，但 Modifier 也可能来自非 Effect 的授予实例。

更合适的是中立的授予身份，EffectHandle 只是其中一种上层来源。

`Talent / Upgrade / Summoner` 作为诊断分类不必然违反分层；**真正的问题是底层是否根据这些分类执行不同业务，以及新增来源是否必须修改计算内核。**

**3．数值 Modifier 不能顺手吞掉权限。**

文档提到 RunRule，却只在 `EModifierDomain` 中列出 Attribute、SkillParam、Damage。这不是一定要补一个枚举，而是需要明确设计决定：

- 人口上限、抽取权重等数值是否复用同一个聚合函数；
- 幻化权限如何表达允许与禁止；
- 多个规则冲突时谁优先。

“禁止幻化”不能编码成 `TransformPermission = 0` 后再套百分比修饰。

**4．`ResolveOutgoingDamageModifier()` 返回一个 float，语义不完整。**

如果输出修饰支持：

```text
固定增加 10
百分比增加 20%
独立倍率 ×1.5
```

一个没有基础伤害输入的 float，无法自然同时表达这三者。

可以返回明确的聚合结果：

```text
固定加值
普通百分比
独立倍率
```

也可以让函数接受原始伤害并返回结算后的伤害。需要选一个清楚的契约，而不是把所有结果继续叫 `Modifier`。

**5．“统一 Resolver”应理解为统一公式，不是唯一万能对象。**

共享有限的数值聚合规则是好事；建立一个同时认识伤害、人口、抽卡、权限、技能和天赋的 Resolver，就重新形成了高耦合中心。

## 六、它的伤害示例与当前项目不一致，不能直接据此迁移

这里有三处必须修正。

**1．项目当前没有文档假设的统一 Attack。**

现有 [FSkillDamageSpec::Evaluate](../Source/MineLearning/Combat/CombatConfig.cpp) 使用：

```text
固定伤害
＋ 力量 × 系数
＋ 敏捷 × 系数
＋ 能量 × 系数
```

文档大量使用：

```text
Attack × QCoefficient
```

作为抽象示例没有问题，但它已经把“接入 Attack”写进开发步骤，这就不再只是示例。

必须明确：

- 保留三维公式，在输入和输出阶段增加修饰；
- 还是正式改变数值模型，增加 Attack 并迁移现有配置。

**我建议首版保留三维公式。** 不为了验证修饰系统额外引入一个尚未定义用途的新攻击属性。

**2．Gunner 的 Q 是输入键，不是现有独立技能 ID。**

当前 Gunner 射击提交的是 `SkillId = Primary`。因此开发计划中的“Gunner Q Damage”不能直接当现有技能配置。

应使用技能语义标识，而非键位。调整按键映射后，强化不应该换作用对象。

**3．黄金爆头已经存在，且当前实现使用权重归一化。**

现有 [RollShotResult](../Source/MineLearning/AI/GunnerCharacter.cpp) 在黄金、普通爆头、身体命中、未命中之间进行权重抽取。

因此：

```text
GoldenChance +20%
```

必须明确是：

- 权重提高 20%；
- 实际概率提高 20%；
- 实际概率增加 20 个百分点。

不能直接把当前权重当成 `[0,1]` 的最终概率。

如果把已有黄金爆头改成天赋解锁，还需要明确默认配置和旧玩法是否保留。不能把一个已经存在的能力当成从零新增而忽略兼容性。

## 七、Snapshot 与 Live 的规则仍然不够确定

对应[第 21 节](C:/Users/gh/Downloads/MineLearning_Roguelite_GameplayRuntime_Architecture.md:1962)。

“每次激活 / 每次命中读取当前有效参数”实际上包含了两种不同规则。

例如三连发：

```text
第一发以后获得攻击强化
第二、三发是否提高伤害？
```

必须有唯一答案。

建议按数据分开确定，而不是对整个技能只写一个 Snapshot/Live：

| 数据 | 建议首版时机 |
|---|---|
| 攻击间隔、连发计划、动画速度 | 激活时锁定 |
| 一次攻击的来源伤害参数 | 明确选择激活或命中时，整个技能遵循同一契约 |
| DoT 的来源伤害贡献 | 施加时锁定 |
| 目标是否存活、无敌、当前减伤 | 每次实际伤害时检查 |
| 连锁深度与触发预算 | 沿根事件传递 |

“DoT 创建时 Snapshot”不应该意味着目标之后获得无敌仍然继续扣血。

同样，不能先快照包含增伤的伤害，命中时又把同一来源增伤加一遍。

这与当前代码还有实际冲突：现有 [CanDamageTarget](../Source/MineLearning/Combat/CombatDamageSubsystem.cpp) 要求来源 Actor 有效且存活。以后要支持施加者死亡后持续伤害继续存在，必须调整伤害来源契约，而非单纯增加几个 Context 字段。

`OriginalSource` 可以有单位身份，但 `DamageCauser` 可能是投射物或区域 Actor，不宜无条件都定义为必须注册在单位名册里的 `FUnitRef`。

## 八、合体可以简化代码结构，不能简化掉正确性

文档的 `TryFusion` 方向可用，但它列出的八项条件不足以覆盖本项目。

还需要处理：

- 输入单位所属玩家和阵营；
- 单位携带的矿物；
- AI 正在执行的订单和预留；
- 合体后的净人口变化；
- 输出生成后 `BeginPlay`、AI 或委托是否提前产生业务；
- 销毁输入时是否触发现有人口释放回调；
- 提交中重入请求如何处理。

当前 [WorkerDestroyed](../Source/MineLearning/Demo/DemoRunComponent.cpp) 会释放人口。若新合体流程已经更新名册和人口，再销毁输入触发旧回调，就可能重复扣减。

因此建议：

> 首版保留一个局部、可读的合体流程；但它必须完整负责预留、失败释放、提交和通知时机。

另外，“3 Gunner → Lancelot”并不是当前最便宜的框架验证案例。现有购买流程主要覆盖 Carrier 与 OreBuddy；这个案例还依赖 Gunner 招募、兰斯洛特单位及其行为完成。

可以先用已有单位类或测试夹具验证事务，不把新角色交付绑进基础框架验收。

## 九、UE 规范方面：能实现，但示例还缺这些约束

我把文中的 C++ 当作接口草图，不会因为省略宏就判整个设计错误。不过，如果要成为施工文档，以下内容必须写清楚。

| 项目 | 需要补充的约束 |
|---|---|
| 反射结构 | 真正使用 `USTRUCT` 的类型需要完整反射声明；需要编辑、序列化或 GC 跟踪的字段按用途添加 `UPROPERTY` |
| UObject 引用 | 区分拥有关系、弱引用和软资源引用；不是写了 `TObjectPtr` 就自动解决 GC |
| TMap 键 | `FEffectHandle` 作为键需要相等比较与 Hash |
| Handle 封装 | 文中 Value 是 public，却又要求外部不能修改，代码形式与约束不一致 |
| Handle 唯一性 | 每个 EffectComponent 都从 1 开始时，必须限制句柄归属，防止误传到另一组件删除同号效果 |
| Gameplay Tags | 增加项目依赖，登记标签，明确精确匹配与父级匹配 |
| Effect 生命周期 | 明确创建、刷新、到期、主动移除、EndPlay 与换形态清理 |
| 数据校验 | 优先接入 UE 的资产校验机制，不只在游戏启动时打印错误 |
| Actor 初始化 | 不依赖多个组件 `BeginPlay` 的隐含顺序完成属性、效果和生命装配 |

Epic 明确说明，`TObjectPtr` 作为受 GC 跟踪的强引用需要相应的 `UPROPERTY` 用法；自定义 `TMap` 键需要比较及哈希支持。[Object Pointers](https://dev.epicgames.com/documentation/unreal-engine/object-pointers-in-unreal-engine)、[TMap](https://dev.epicgames.com/documentation/en-us/unreal-engine/map-containers-in-unreal-engine)

Gameplay Tags 可以直接使用 UE 已有的标签与查询能力，但不能把标签当成任意字符串而不维护词典和匹配语义。[Gameplay Tags](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-gameplay-tags-in-unreal-engine)

配置校验则可以落到 `IsDataValid` 或编辑器校验器，而不需要自建一个庞大的验证框架。[Data Validation](https://dev.epicgames.com/documentation/unreal-engine/data-validation-in-unreal-engine)

**Effect 的时间规则还需要补齐。**

三种 StackPolicy 并没有回答：

- 刷新后是否重置周期伤害节奏；
- 到期时刻与周期触发重合，先执行哪一个；
- 满层后再次施加是否延长时间；
- 多来源共享层数时，谁获得伤害和击杀归属。

首版可以主动收窄，例如暂不支持跨来源合并 DoT。这样比先实现一个看似通用、实际上语义不完整的叠层系统更简单。

跨幻化状态也建议记录到期时间，而非仅保存“剩余三秒”。否则在其他形态停留十分钟后切回来，效果可能仍然剩三秒。

## 十、“保留 Authority 语义”合理，但不能当作多人已预留完成

对应[第 27～28 节](C:/Users/gh/Downloads/MineLearning_Roguelite_GameplayRuntime_Architecture.md:2167)。

赞同客户端只提交意图、权威端计算结果。

但以下事项仍需独立设计：

- 哪个对象承载请求入口；
- 哪些状态属于本局公共状态，哪些属于某个玩家；
- 哪些客户端应该收到哪些信息；
- 中途加入、重新连接和 Pawn 替换如何同步；
- 本地局外档案与服务器认可的成长数据如何区分。

特别是 `PurchaseTalent` 不一定属于当前世界里某个 Actor 的 Authority 判断。它可能发生在主菜单，拥有者是档案系统。把所有操作都统一套 `HasAuthority()`，语义反而会变错。

UE 的网络 Owner、Owning Connection 会影响 RPC 路由和复制可见性；这与玩法上的阵营归属并不等价。[Actor Owner and Owning Connection](https://dev.epicgames.com/documentation/en-us/unreal-engine/actor-owner-and-owning-connection-in-unreal-engine)

还要注意：当前 `HealthComponent`、`CombatComponent` 已经有复制代码。文档的“当前可以不 Replicate”应解释为暂不新增完整网络支持，不能据此删掉已有复制行为。

另外，GAS 也并不要求一接入就实现预测、完整 GameplayCue 和所有网络能力。**暂不整体迁移 GAS 的结论可以保留，但理由应是当前迁移收益与成本，而不是把所有 GAS 功能都当成必须一起采用。**

## 十一、简单性方面，我会进一步收缩三个地方

**1．不要把第 41 节目录直接当作必建文件清单。**

现在可以明确语义，不必立即创建二十多个文件和独立组件。

建议优先保留、扩展当前的实际拥有者：

| 职责 | 首版落点建议 |
|---|---|
| 属性与技能参数查询 | 当前 Combat 能力边界，内部复用小型聚合函数 |
| 临时效果实例与计时 | 一个单位 EffectRuntimeComponent |
| 已授予能力 | 简单的能力来源集合；有独立消费者和生命周期价值后再拆组件 |
| 本局选择与奖励 | 一个跨 Pawn 的本局状态拥有者 |
| 正式伤害结算 | 现有 CombatDamageSubsystem |
| 生命变化 | 现有 HealthComponent |
| 数值解释 | Resolver 的可选明细输出 |

这并不是要求所有代码挤进旧组件，而是先避免新增一层只负责转发。

**2．RunBuild 不能把推导结果变成多份权威状态。**

文档同时列出：

```text
SelectedUpgradeIds
UpgradeRanks
Run Modifiers
Granted Features
Build Tags
```

这些可以同时存在，但必须明确：

- 哪些是权威输入；
- 哪些是派生结果；
- 派生结果只能由谁更新。

通常一份 Upgrade ID→等级的记录就能表达大部分选择状态；顺序确实影响玩法时再记录顺序。

已经确认的 RewardOffer 保存候选即可，不必为了“防止重开 UI 重抽”强制每个 Offer 再存一份随机状态。随机流状态放在真正需要继续抽取的拥有者上。

**3．Explain 必须使用同一条计算路径。**

不能再写一套“解释用公式”。

伤害发生时的解释还要基于当时输入，不能事后查询当前 Buff 再推测之前为什么打了 1344。

首版按需收集本次计算明细即可。默认每次 Getter 都构建字符串或长期保存每个命中事件，属于不必要成本。

## 十二、我建议采用的修正版实施顺序

这份文档先做大量底层概念，再接真实技能，仍然有一点“先建框架再验证”的倾向。

我建议更早形成一个真实闭环：

1. **先定四个契约**：修饰主体与来源、能力资格与授予、参数求值时机、状态变化通知。
2. **用现有 Gunner Primary 接入两个独立数值来源**：保持三维公式，验证添加、移除和 Explain。
3. **接入一个三秒攻速效果**：同时验证实际连发、到期恢复、换形态与销毁。
4. **接入三选一与新单位初始化**：证明本局记录、现有单位和新单位结果一致。
5. **验证一个行为能力**：可利用已有黄金命中事件做短时狂热；穿透涉及命中流程改造，不一定是最便宜的首例。
6. **再接天赋快照和召唤师**。
7. **最后做一个依赖已就绪的合体配方**。

我会把以下情况作为设计是否真正落地的验证题：

- 不打开属性面板，最大生命强化是否立即正确生效？
- 两个独立来源授予穿透，移除一个是否仍然保留？
- AI 改为玩家控制后，条件修饰是否及时失效？
- DoT 来源死亡后，伤害和击杀归属是否仍符合规则？
- 切换形态后，限时效果是否按既定时间继续流逝？
- 合体失败是否保留资源，成功是否只结算一次人口？

**我的最终意见是：采纳它的语义补充，修改中央查询、资格授予和时间身份契约，缩减首版结构后再实施。** 它比上一版更完整，但“概念更多、更正式”本身不代表代码会更简单；只有这些运行时问题得到明确答案，才真正符合我们的“实现简单、方便扩展、语义正确”。

第 40 节关于 X5 Lua 的结论，本轮没有对应源码可核对，我不会把它作为方案正确性的证据。
