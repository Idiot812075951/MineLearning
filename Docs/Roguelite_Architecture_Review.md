# 支持机械单位构筑玩法的程序框架——架构 Review

> 评审日期：2026-09-26。本文保存自本次对话中的文档二，未新增设计结论。
>
> 评审依据是[玩法草案](../肉鸽系统.md)、当前工作区 C++ 实现及相关项目文档。已通过 Unreal MCP 成功查询到本项目 Combat 资产；评审期间没有运行编译、测试或 PIE。文中区分代码现状和设计建议，不把方案当成已验证实现。
>
> 用户提到的“高耦合低内聚”，按前后文真正希望的 **低耦合、高内聚** 设计。
>
> 配套文档：[功能 Review](Roguelite_Function_Review.md)。

## 1．架构结论

建议采用：

> **保留现有统一伤害与物流执行链，补充有限的属性/效果运行时，把局外解锁、局内构筑和规则装配放在上层。**

第一阶段不建议直接把整个项目改造成 GAS，也不建议做一个支持任意逻辑的“万能 Buff 脚本系统”。

这里的前提是：**继续以当前本地单人玩法为近期目标，保留权威端校验，不宣称支持完整多人。**

如果多人合作、预测施法和大量网络状态同步已经进入近期计划，应在实施前重新选择 GAS，不能等自研运行时铺开后再假定能够低成本替换。

Epic 的 GAS 已提供效果持续时间、属性修改、叠层及相关生命周期机制，确实适合复杂能力系统。但它不会代替本项目的天赋、随机池、生产和合体业务设计。[Epic：Gameplay Effects](https://dev.epicgames.com/documentation/unreal-engine/gameplay-effects-for-the-gameplay-ability-system-in-unreal-engine)

| 方案 | 对本项目的评价 |
|---|---|
| 在角色中继续增加 Buff 判断 | 初期快，长期会使角色、天赋、召唤师相互依赖，不建议 |
| 有限的原生效果内核＋现有技能执行 | 推荐当前阶段；迁移边界较小，但必须限制自研范围 |
| GAS 承担属性、效果及能力生命周期 | 适合明确的复杂联网需求；当前迁移成本较高，需要专项方案 |

这里的“有限”是明确限制：数值修饰、标签授予、持续时间、几种固定叠层策略。新技能行为仍然写正常的 C++ 业务代码，不把任意逻辑塞进配置解释器。

## 2．现有代码里应该保留什么、先改什么

有两个特别容易误判的现状：

- 项目并非完全没有攻速、移速。采矿组件已有局部 `AttackSpeed`，Gunner 有 `FireInterval`，角色移动组件有速度；**缺的是统一的有效参数来源。**
- 当前红莲已有基于生命阈值的处决。草案里的“溶解积累、传播”是新增机制，不能把现有处决改名就视为完成。

## 3．依赖分层：先划清边界，再决定类名

下面是建议的编译依赖方向。上层可以使用下层，下层不得包含或查询上层业务类型。

```text
表现与输入
  UMG、输入路由、动画/特效表现
              ↓ 命令 / 查询
局外与局内应用层
  天赋购买、开局装配、强化选择、召唤师装配、合体流程
              ↓
具体能力与领域执行
  Gunner 射击、采矿、Guren 技能、幻化、生产
              ↓
基础能力
  属性修饰、状态效果、生命、伤害结算、库存、单位登记
              ↓
公共值类型
  稳定 ID、标签、请求/结果、修饰运算、来源与句柄
```

状态变化事件可以由下层发出、上层订阅，但下层不持有上层对象，因此不形成反向代码依赖。

应明确禁止：

```cpp
// 属性或伤害层不应该出现：
if (TalentTree->HasTalent(...))
if (SummonerId == ...)
if (DemoRun->GetPhase() == ...)
Cast<AGunnerCharacter>(Owner)
```

正确调用关系是：

```text
召唤师装配逻辑
→ 根据召唤师规则，给符合条件的单位登记伤害修饰

伤害结算
→ 读取已经生效的修饰
→ 完成伤害
```

同理，合体系统可以检查开局授予的配方资格；库存组件只处理资源预留，不知道兰斯洛特是什么。

初期可以保留在现有 Runtime Module 内，用目录和 include 约束落实边界。真正拆 UE Module 时，再从不依赖项目上层的基础部分开始；不为了图好看先拆十个模块。

## 4．状态归属与生命周期

这是比继承关系更重要的设计。

| 状态 | 权威拥有者 | 生命周期 |
|---|---|---|
| 已购买天赋、局外货币 | 局外档案 | 跨局，通过 SaveGame 持久化 |
| 本局解锁快照、召唤师、随机种子、阶段 | RunSession | 从开局到结算 |
| 已选择强化及等级、待选择奖励 | 本局玩家构筑记录 | 跨 Pawn，本局结束清理 |
| 已拥有单位与人口成本 | 单位名册 | 单位加入到离开本局 |
| 单位当前生命、局部异常状态 | 单位运行时 | 单位存续期间 |
| 玩家跨幻化保留的生命、冷却、弹药等 | 玩家形态状态记录 | 本局内跨身体切换 |
| 动画、瞄准目标、抓取过程、寻路 | 当前 Pawn/技能执行者 | 当前身体或当前动作 |
| 卡牌定义、配方、单位配置 | 不可变配置资产 | 资源生命周期 |

可以从当前 `UDemoRunComponent` 的宿主位置起步：本地单人时，PlayerController 上的组件足以承载本局玩家状态；不要一开始就增加一套并行的全局 RunManager。

`UMiningGameSubsystem` 当前只是创建一个内存中的 `UMiningPlayerData`，**GameInstance 生命周期不等于存档**。局外系统需要显式加载、保存、版本迁移。

一条约束必须坚持：

> 保存基础数据、选择结果和必要运行状态；最终属性、已解锁集合等可推导结果，不再保存第二份可编辑真相。

为性能或网络维护的派生快照可以存在，但必须明确只读，由权威状态统一生成。

## 5．属性：三维可以保留，但不应承担所有数值

建议分成三类：

| 类别 | 示例 | 归属 |
|---|---|---|
| 单位通用属性 | 力量、敏捷、能量、最大生命、基础移速、攻速倍率、冷却倍率 | 单位属性运行时 |
| 技能参数 | 抓取距离、黄金爆头倍率、连锁半径、穿透数量 | 对应技能参数 |
| 局内规则参数 | 人口上限、奖励权重、合体费用 | 本局规则 |

**人口、抽卡权重不要塞进角色属性组件。黄金爆头概率也不要强行成为所有单位共有属性。**

三维的定位建议保持当前伤害系数用途。不要自动规定“敏捷同时增加攻速、移速、暴击”，除非这是明确的数值设计，否则一次加敏捷会在多个系统产生难以评估的放大。

通用数值修饰采用固定公式，例如：

```text
最终值 =
Clamp(
    (基础值 + 固定值加成总和)
    × (1 + 同类百分比加成总和)
    × 独立倍率乘积,
    下限,
    上限
)
```

对应示例：

```text
基础移速 300
固定加成 +30
普通移速加成 +20%
独立减速倍率 ×0.8

最终移速 = 330 ×1.2 ×0.8 = 316.8
```

必须明确哪些配置进入哪一项，禁止所有百分比默认独立相乘。

攻速使用倍率：

```text
实际攻击间隔 = 基础间隔 / 有效攻速倍率
```

所以攻速 +20% 对应除以 1.2，并非把间隔乘以 0.8。

冷却采用独立语义：

```text
实际冷却 = 基础冷却 × 有效冷却倍率
```

例如冷却缩减 15% 对应 0.85。所有倍率验证有限值和合理范围，避免零间隔、负冷却及溢出。

## 6．效果运行时：用来源句柄解决叠加与撤销

建议引入一个单位效果组件，负责当前生效的效果实例。属性计算可以先作为其中的纯计算部分，不必为了名称再拆一层只有转发功能的组件。

效果定义与实例分离：

| 数据 | 内容 |
|---|---|
| 效果定义 | 修饰列表、持续策略、叠层规则、最大层数、可授予状态标签 |
| 活跃实例 | 定义 ID、句柄、来源、目标、实际层数、到期时间、必要快照 |

最小接口可以表达为：

```cpp
FEffectHandle ApplyEffect(const FEffectSpec& Spec);
bool RemoveEffect(FEffectHandle Handle);
float GetAttribute(EUnitAttribute Attribute) const;
```

这是建议的接口轮廓，不是已实现代码。

关键规则：

- 移除通过句柄定位，不能靠“把之前加的数减回去”。
- 独立来源独立管理，移除召唤师加成不能移除同名卡牌加成。
- 叠层键明确包含哪些内容，例如效果定义＋来源。
- 首版只支持确实需要的几种策略：独立实例、增加层数并刷新时长、刷新时长不增层。
- 重复移除安全，不重复广播业务结果。
- 到期、销毁、换形态时成对解除绑定和计时器。
- 永久局内效果不使用一个很长的持续秒数模拟。

“即时回血”是一次命令，不属于可以撤销的持续修饰。移除授予回血的卡牌，不能把已经恢复的生命扣回去。

上层负责选择目标，例如“本方所有 Gunner”。效果内核只接受已经确定的目标，不自己遍历全世界寻找召唤师或阵营构筑。

## 7．技能参数和技能形态，不能都塞进属性系统

技能参数建议使用：

```text
技能标识＋参数标识＋数值修饰
```

但每个技能必须声明自己支持的参数及类型，例如：

```text
Gunner.Primary：
  FireRate
  GoldenHitWeight
  GoldenHitDamageMultiplier
  PierceCount

Guren.Q：
  GrabRange
  ExecuteHealthFraction
```

配置中写了不支持的参数，应在校验阶段报错，而不是运行时默默忽略。整数数量、概率、距离和倍率也不能混用同一套无约束浮点值。

**技能行为则由具体技能实现。**

例如：

- 穿透：射击命中流程支持多个沿线目标；
- 分裂：命中后生成后续射击或投射物；
- 黄金爆头爆炸：订阅确认的黄金命中结果并产生范围伤害；
- 连锁采矿：订阅矿物耗尽事实并寻找后续合法矿物；
- 黄金风暴：满足触发条件时授予临时攻速效果。

局内强化只负责授予对应功能或参数修改。伤害系统不应该出现 `if (HasGoldenStorm)`。

**觉醒也不必单独建设一个新的执行引擎。** 它是拥有特殊前置和互斥规则的高级强化，授予已有技能功能组合，必要时替换明确的技能变体。

数据驱动的边界是：

> 已实现机制的数值和组合可以配置；新的行为机制仍然需要实现与测试。

所以“加一个配方就能得到兰斯洛特”只有在兰斯洛特的 Pawn、技能、AI、输入与表现已经存在时才成立。

## 8．伤害结算：扩充上下文，保持唯一入口

现有伤害公式可以作为基础，不需要为了 Buff 先重写全部战斗。

建议稳定为：

```text
技能执行确认命中
→ 形成伤害上下文
→ 校验目标与权威端
→ 计算技能基础值和属性贡献
→ 应用技能/来源伤害修饰
→ 应用命中类型倍率
→ 应用目标减伤或特殊结算规则
→ HealthComponent 提交生命变化
→ 发布伤害及死亡事实
→ 上层响应连锁、吸血、奖励等
```

伤害上下文建议逐步补充：

- 原始发起者、实际造成伤害的对象、目标；
- 技能 ID；
- 命中类型，如普通、黄金命中；
- 根事件 ID、后续触发深度；
- 必要的位置和数值快照；
- 是否允许产生二次触发。

不要把所有业务都挤进现有 `Multiplier`。否则无法知道加成来自爆头、召唤师、技能专精还是连锁衰减，展示和调试也无法解释结果。

`bExecute` 的判断仍属于技能规则；基础结算只执行经过权威技能流程确认的结果。未来添加网络请求时，客户端只能提交意图，不能自行提交可信的伤害倍率或处决资格。

**需要特别保护的已有规则：**

- 红莲 Q 在真实接触后锁定处决资格；
- 降临按命中前生命判断；
- 非致死保护不能被普通 Buff 绕过；
- 矿物掉落与耗尽仍由实际生命结算驱动。

**连锁不能直接无限递归调用。**

建议把后续触发加入有序队列，配置最大深度、总触发预算和目标去重规则。一次击杀只能发出一次死亡事实；合体移除和普通销毁不冒充死亡。

当前入口要求伤害来源仍有效且存活。以后如果要支持“发射后角色死亡，子弹仍然命中”，需要增加由权威端创建的伤害来源快照。不能简单删除所有来源校验。

## 9．攻速、移速和生命上限，需要接到真实执行者

这是属性系统最容易“面板完成、玩法没完成”的地方。

- **Gunner 攻速**：不仅影响 `NextAllowedFireTime`，还涉及连发时序与动作占用。当前连发存在固定时间调度，不能只改 FireInterval。
- **OreBuddy 攻速**：接入采矿 Montage 速率及命中计划，保证每个命中只执行一次。
- **移速**：由移动逻辑读取有效速度，再计算冲刺倍率。当前 OreBuddy 冲刺会持续写 `MaxWalkSpeed`，直接从 Buff 写这个字段会被覆盖。
- **冷却变化**：首版建议已开始的冷却不追溯重算，新施放使用新参数。
- **攻击中参数变化**：首版按一次攻击或一次技能激活锁定相关参数；下一次执行读取新值，减少动作中途变速引起的重复命中。
- **最大生命变化**：新增专门的更新规则，不能调用目前会回满血的 `InitializeHealth`。

建议最大生命改变时默认保持生命比例，死亡目标不因此复活。若某强化还附带治疗，单独声明治疗效果。

最大生命的基础值和修饰应有唯一来源；Health 保留当前生命及合法结算职责，不再维护另一套独立可编辑的最大生命配置。

## 10．局内强化与随机池

建议的数据结构：

| 定义 | 主要内容 |
|---|---|
| UpgradeDefinition | 稳定 ID、目标范围、等级上限、前置、互斥、权重、效果与技能功能授予 |
| 本局选择记录 | 强化 ID、等级、选择序号 |
| RewardOffer | 奖励 ID、固定候选列表、是否已领取 |
| 开局资格快照 | 本局允许的内容、召唤师与主题 |

抽取顺序应明确：

```text
内容全集
→ 本局资格允许
→ 目标能力适配
→ 前置满足
→ 未达上限
→ 不冲突
→ 计算有效权重
→ 无放回抽取候选
→ 保存本次候选
```

健壮性要求：

- 同一次奖励不重复展示同一内容。
- 合法候选不足三项时，有明确的保底或少项展示策略。
- 权重全为零、内容缺失、等级满级均有确定行为。
- 关闭菜单再打开不能重新抽。
- 用奖励 ID 防止重复领取。
- 领取时重新校验并一次性提交选择与效果，不能先扣奖励再加载失败。
- 随机流与战斗随机分开，避免多打一枪改变下一次强化候选。

“当前没有某单位”的强化不能一律删除。如果该单位属于本局已选方向、可以合理获取，可以作为投资选项；否则容易让构筑只能追随当前已有单位。

## 11．天赋与召唤师：上层转换成中立能力

天赋定义只需要：

```text
节点 ID、花费、前置节点、解锁内容、可选挑战条件
```

档案保存已购买节点和货币。可用配方、可选召唤师、可入池强化由已购买节点推导。

开局时生成资格快照。本局运行期间不要在每次伤害、抽卡、生产时回查天赋树。

召唤师配置则由开局装配转换成不同领域能理解的输入：

| 召唤师规则 | 下层收到的内容 |
|---|---|
| 人口上限提高 | 本局人口限制修饰 |
| AI 单位伤害提高 | 目标单位的伤害修饰 |
| 玩家控制时强化 | 控制权变化后增删对应效果 |
| 禁止幻化 | 幻化权限拒绝结果 |
| 某系列更容易出现 | 奖励权重修饰 |

伤害系统不知道“AI 指挥官”；幻化执行不读取召唤师资产；卡池不读取天赋树节点。

召唤师附加能力也使用稳定资格与明确的能力授予，不再做第二套召唤师专属 Buff 引擎。

存档至少考虑版本号、稳定内容 ID、缺失内容处理，以及一次结算只发一次奖励。保存失败不能反馈成“购买并保存成功”。

## 12．单位名册与合体事务

当前人口维护需要先收敛。

`PurchaseRobot` 一方面用 `Workers.Num()` 检查固定上限，另一方面调用 `UsePopulation(1)`，且未以其返回结果决定购买成功。上限一旦可以被召唤师修改，两套状态就可能不一致。

建议：

```text
实际人口 = 单位名册中有效单位的人口成本之和
可用人口 = 有效上限 - 实际人口 - 尚未提交的预留人口
```

现有 Workers 集合可以迁移成为唯一单位名册，不再另外维护一个永远需要手动对齐的 PopulationUsed。

合体配方至少定义：

```text
配方 ID
输入单位类型与数量
资源费用
输出单位定义
输出人口成本
必要资格
生命/状态继承规则
可选形态解锁奖励
```

**合体是事务流程，不是 Spawn＋Destroy 循环。**

建议执行顺序：

1. 校验单位 ID 不重复、所有权正确、仍存活、符合配方。
2. 完成工作收尾，处理携带物与物流预留。
3. 预留输入单位和资源，阻止其他请求重复消费。
4. 预加载输出资产，创建尚未参与 AI、伤害和物流的候选单位。
5. 再次确认输入和资源有效。
6. 提交资源、替换单位名册、完成状态转换，统一结算人口。
7. 启用输出单位，移除输入，发布一次合体完成事实。

提交前失败释放预留，原单位与资源保持有效。提交阶段必须避免可失败操作和可重入回调；需要将通知延迟到内部状态一致之后。

这里不能声称 UE 的多个 Actor 操作天然具有数据库事务性，必须由流程保证。

现有库存只按物品类型累计预留。合体与订单并存后，建议增加事务句柄及批量预留/提交，确保一笔操作不能释放另一笔操作的库存。

**合体继承不要求和最终属性。**

推荐输出单位使用：

```text
输出单位基础配置
＋ 本局适用于输出单位的强化
＋ 配方明确允许转换的个体状态
```

例如所有 Gunner 共享的一张伤害强化，不会因为合并了三只 Gunner 而变成三层。

## 13．幻化：保留构筑，明确保留哪些身体状态

需要把两件事分开：

- 构筑选择随玩家本局持续存在。
- 技能执行与动画随身体结束。

建议换身流程：

```text
检查权限与执行状态
→ 准备新身体
→ 恢复该形态必要状态
→ 应用本局匹配的构筑和规则
→ 确认初始化完成
→ 切换控制
→ 收尾旧身体
```

失败时恢复旧控制，不消费额外资源，不提前丢失状态。

至少需要显式处理：

- 当前生命；
- 弹药与已支付的装填；
- 技能冷却；
- 需要跨幻化持续的临时状态及到期时间。

否则新 Pawn 初始化会产生换身回满血、刷新冷却、清除负面状态等漏洞。

这不要求序列化整个 Pawn。只保存玩法明确要求延续的状态，动画进度、瞄准对象和寻路可以正常终止。

玩家形态和 AI 单位继续作为两种身份处理。未来如果选择接管真实单位，应另行设计控制权转移，不与本次框架悄悄混合。

## 14．UI 与业务的数据契约

UI 使用 UMG Widget Blueprint，负责显示和输入表达。

例如：

```text
强化界面提交：选择 RewardId 中的 UpgradeId
合体界面提交：用这些 UnitId 执行 RecipeId
天赋界面提交：购买 TalentNodeId
```

业务层返回成功/失败结果并发布权威状态变化。UI 不自行扣资源、推导前置、计算伤害或决定可合体单位。

技能说明读取与执行相同的有效参数查询。可以在表现层组合文字，但不能再复制一份伤害公式。

当前 `CombatComponent::GetPanelData` 中的 Gunner、Guren 专属分支需要迁出；这是必须处理的反向依赖，而不是单纯调整代码风格。

## 16．建议实施顺序与验收门槛

| 阶段 | 目标 | 必须证明 |
|---|---|---|
| A．整理边界 | 明确单局生命周期、人口和状态归属 | Demo 现有闭环不退化 |
| B．数值内核 | 属性修饰、效果句柄、真实速度接入 | 多来源叠加与移除正确 |
| C．最小构筑 | 奖励候选、选择记录、新单位继承 | 不重复领取，换身不丢强化 |
| D．一个复杂技能变化 | 穿透或黄金风暴等单个案例 | 参数、执行、表现与连锁边界一致 |
| E．局外系统 | 存档、少量天赋、召唤师装配 | 资格快照稳定，结算幂等 |
| F．一个合体配方 | 单位与资源事务 | 失败无损、成功无复制与人口漂移 |

未来测试重点应包括：

- 两个来源加同一种属性，移除任意一个后结果正确。
- 效果到期、单位销毁、换形态时没有遗留回调。
- 生命上限变化不意外回满或复活。
- 攻速变化不导致重复射击、重复采矿命中。
- 新生产单位正确继承阵营强化。
- 合体不会把共享强化重复叠加。
- 合体材料重复、生成失败、资源失效时不吞资源。
- 换形态不能刷新生命、弹药或冷却获利。
- 一次死亡只触发一次奖励，连锁存在明确上限。
- 移除全部 UI 后，生产、伤害、选择和合体业务仍可执行。
- 属性、伤害、库存等基础层不引用天赋、召唤师、Demo 或具体 Widget。

已有的统一伤害、Guren 生命周期、Gunner 玩家形态、OreBuddy 冲刺及 Demo 生产测试可以作为回归基础。本次只检查了相关代码，没有执行这些测试。

**这份设计最应守住的约束是：上层决定授予什么能力，下层只执行自己认识的能力。** 新增一个天赋节点，不应该要求修改伤害系统；新增一个召唤师，不应该要求给所有角色增加类型判断；新增一个已有机制的强化，不应该要求再写一条贯穿 UI、角色、伤害和 Demo 的分支。
